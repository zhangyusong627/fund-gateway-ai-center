## R1 — M4「编译通过但语义错误仍能拦截」缺实现策略

- **关联**：fund-integration（M4 核心验收句）；M0-D2/D5 机制相关。
- **问题**：隔离编译只能证明"语法/类型正确"，拦不住"逻辑语义错"。ROADMAP 写了验收句（"即使代码编译通过，语义错误也必须能被拦截"），但没有写用什么机制拦。
- **不解决的后果**：M4 只能演示"能编译的代码生成"，核心验收句落空；或临时凑一个不可复现、不可讲述的判官。
- **建议方案（供裁决，可组合）**：
  1. **收敛"语义正确"的定义**：= 与已发布资方契约字段对齐 + 通过该接口的最小 golden 断言集（字段齐全、错误码/幂等键正确、类型与契约一致）。把开放式"对错"收敛成可断言的检查。
  2. **分层拦截**：确定性检查优先（契约对齐 + golden 断言 + 静态规则）；仅对确定性检查覆盖不到的部分，用 LLM judge 产出"可疑点"，**由人工复核**，不让 judge 直接下终审。
  3. **M0 加一次 30 分钟 spike**：用 D2 的结构化输出经验跑通"生成 → 隔离编译 → golden 断言"最小链路，验证拦截可行性；结论进 ADR。
- **待裁决点**：拦截策略采用 1/2/3 的哪种组合；是否接受"语义拦截 = 契约对齐 + golden 断言 + judge 建议人工复核"作为验收口径。

## R2 — guardian「规则 vs Agent」对比缺评测集与计分口径

- **关联**：fund-guardian（M1 验收）；M0-D5 首批验收集。
- **问题**：对比需要一个"带金标准的合成故障集 + 明确指标"。现在只有 D5"首批验收集"的概念，评测方法未落。
- **不解决的后果**：M1 的"对比规则 vs Agent"退化成看演示，无法量化，也就无法回答"Agent 到底值不值"。
- **建议方案**：
  1. M0/D5 定评测集 schema：每个样例 = 现象描述 + 可用证据 + 金标准结论 + 是否"证据不足应停止"。
  2. 指标明确，例如：金标准结论命中率、缺证时是否正确停止、证据引用是否真实存在（防幻觉）、误报率。规则与 Agent 跑同一集，出对比报告。
  3. 规模不必大，20~30 条合成样例即可支撑对比；金标准由学习者标注（保证场景贴合其真实经验，但语料仍是合成的）。
- **待裁决点**：评测集与指标口径是否按此定；金标准标注是否由学习者在 M1 前完成。

## R3 — 资方契约字段 schema 未冻结（关联 HANDOFF Q1）

- **关联**：fund-knowledge / fund-guardian / fund-integration 三处；M1/M3 前置。
- **问题**：B 发布契约、A 当证据读、B 生成骨架全都 keyed 在"契约长什么样"上。共享字段底线 HANDOFF 已列出（资方标识、接口标识、来源、版本、生效时间、确认状态…），但 v1 字段清单未冻结，Q1（与真实业务表是否对齐）仍开着。
- **不解决的后果**：schema 建错三处返工。
- **建议方案**：
  1. 在 M1 开工前，用合成资方（恒誉 / 云腾 / 衡丰）定义契约最小字段集并**用 ADR 冻结 v1**，后续只加不改。
  2. Q1 按"合成 schema 只需自洽、无需复刻真实业务表"结案——Q1 的真实目的是防简历/讲述失真，而合成数据本就允许与真实表不同；只要口径在面试时不越界即可。
- **待裁决点**：Q1 是否按上述口径结案；契约 v1 字段清单由谁拍板。

## R4 — RAG 地基依赖未验证（关联 HANDOFF Q7）

- **关联**：M3（pgvector/索引/检索）；M0-D4（最小检索评测）。
- **问题**：Docker 未装、pgvector 没跑过、Embedding 提供商 D4 才冻结——但 D4 做评测时就得有库和提供商。
- **不解决的后果**：M3 起点被环境卡住，或 D4 评测临时换方案导致不可比。
- **建议方案**：M0 内做一次 30 分钟离线 spike：Docker 起 PostgreSQL + pgvector，用一个临时 Embedding 候选跑 10 条合成样例，确认连通、写入、查询；结论进 ADR。Embedding 正式选型仍按 D4 评测后冻结，spike 只解"环境可行"，不解"选哪家"。
- **待裁决点**：spike 是否排入 M0；临时候选由谁指定。

## R5 — M2 状态持久化与"DB 延后到 M3"时间线矛盾

- **关联**：M2（审批、状态持久化、重启恢复、审批过期）。
- **问题**：M2 要持久化状态并测"进程中断/重启"路径，但 PostgreSQL 规划 M3 才接入。中间用什么持久化没定。
- **建议方案**：
  - 方案 a（推荐）：M2 用本地文件 / H2 做状态持久化。合成场景规模小，足以测"重启后恢复、过期审批被拒"等路径；把数据库引入整体推迟到 M3，减少前置环境。
  - 方案 b：把基础 PostgreSQL 提前到 M2 当状态库，M3 只加 pgvector。代价是 M2 就要装 Docker、维护 schema。
- **待裁决点**：选 a 还是 b。

## R6 — 时间与成本预算偏乐观（关联 Q4 / Q6 / Q8）

- **关联**：总排期；M3 估时；成本预算。
- **问题**：M3 排 3 周偏乐观；学习者并行面试训练（1.5h/天）与可能的求职（Q4）；无月度成本预算条目。
- **建议方案**：
  1. M3 按 4~5 周排，机动预算优先承诺给 M3（沿用 Q6 建议）。
  2. 建立月度 API 成本预算条目（DeepSeek + Embedding 云 API），写进 ADR 或 README（Q8）。
  3. 阶段门禁失败不阻塞总进度，失败知识点进次日复习项滚动消化（沿用 DAILY_PLAN 机制）。
- **待裁决点**：采纳 Q6/Q8 建议；机动预算的分配口径。
