# ADR-017 环境隔离采用数据库级固定连接

状态：已接受

## 决策

在同一个本地 PostgreSQL 实例中使用三个独立数据库：`fund_dev`、`fund_acceptance`、`fund_baseline`。每个数据库继续使用现有的 `knowledge` 与 `guardian` 领域 schema。应用实例通过启动配置固定连接到一个数据库，控制台只展示当前环境，不提供运行时切换连接目标的下拉框。

## 原因

当前代码和初始化 DDL 已经将领域边界明确表达为 `knowledge.*` 与 `guardian.*`。把环境改造成外层 schema 会要求改写大量限定表名、测试、评测 SQL 和迁移脚本，增加误写数据与回归风险。数据库级隔离仍然共用同一个物理 PostgreSQL 存储，能满足开发、独立验收和历史基线分离的目标，并保留现有领域 schema。

## 环境约定

| 环境 | 数据库 | 用途 | 写入策略 |
|---|---|---|---|
| dev | `fund_dev` | 日常开发和调试 | 可写，可重建 |
| acceptance | `fund_acceptance` | 从空环境走完整链路 | 可写，验收后保留 |
| baseline | `fund_baseline` | 历史验收证据和对照 | 默认只读，不用于日常开发 |

环境通过 `CONSOLE_ENVIRONMENT` 和 `CONSOLE_DB_NAME` 指定。禁止在进程运行期间修改连接目标；需要切换环境时重启一个明确标记环境的应用实例。`prod` 不作为本项目环境名，本项目没有真实生产系统。

## 后果

同一 PostgreSQL 实例的物理资源仍然共享，不能模拟生产级资源隔离。数据库创建和 schema 初始化必须显式执行，应用启动不自动清空或重建数据。控制台状态接口返回当前环境，避免演示时误判连接目标。
